# Private candidate rehearsal

The public pgvector reader requires reviewed acceptance and a real activation.
Some acceptance evidence must be measured before activation. An owned restore
therefore has a separate `EngineeringCandidatePin`, resolved from the actual V3
build, complete validation, content seal, physical projection and still-current
v1 predecessor. It contains no v2 activation ID and creates no acceptance row.

`load_candidate` refuses production settings, a database other than the explicit
operator target, a missing independent restore marker, mismatched predecessor,
incomplete or changed validation, unsupported policy and disabled physical
guards. The initial-migration candidate scope ends when any v2 backend activates
for that logical index. Fresh reads repeat these checks; candidate results do
not authorize current source use by themselves.

`CandidateRetriever` reuses the hybrid and Similar pipelines, including bounded
ANN transport, origin verification, immutable bibliography, current permissions,
source lifecycle, and Similar's fresh common final snapshot. Only the explicit
closed union of active and engineering authorities enters these shared private
read helpers. The original active-pin loader remains strict. Public route
selection still requires the exact `ContentRetriever` class and rejects the
candidate subclass. Scientific result filters, saved answers, public response
metadata and public history retain their active-identity requirements.

`create_private_app` exposes only `/health`, `/candidate/similar` and
`/candidate/hybrid`. It has no public routes, history writes, acceptance,
activation or schema endpoints. The owned host operator must bind it to loopback
inside the network-none restore container namespace, with no host port mapping.
No operator request can choose an SQL relation or supply credentials.

Every response states `owned_restore_not_activated`. Hybrid is the shared
candidate phase, not the complete scientific Search or generated Ask response.
Numerical/evidence-condition queries are refused by this private HTTP endpoint;
their complete public-flow gates remain separate. This keeps private component
results from being reported as full-site or scientific acceptance.

The operator may supply a copied, validated frozen query-vector inventory.
Responses then explicitly state `frozen_replay_excludes_provider_latency`.
Missing replay queries fail; there is no provider fallback. Similar never calls
an embedding provider. Replay load evidence covers database/coordinator work
only; live embedding and answer-generation latency require separate evidence.

Real-corpus load still needs the declared arrival rate, source-vector
distribution, error/latency receipts and primary resource guard. Human relevance,
Ask/Similar expert review, native queue/republication, actual recovery and signed
release remain required. Neither a successful private request nor preparation
starts the seven-day production observation window or permits Google retirement.

The initial real-corpus HTTP trial also exposed overhead in the engineering
authority loader: nine SQL round trips per repeated source check. The loader
now uses one target-database check and one closed joined snapshot for the
actual build, validation, content seal, marker, v1 predecessor, absence of a v2
activation and physical guards. Every record digest and predecessor comparison
remains mandatory. No authority is cached and no public reader is changed.
Missing marker relations fail closed. A migrated source CAS invalidates the old
candidate, and disposable tests verify both that invalidation and the two-query
budget. Real HTTP resource/performance acceptance must still be remeasured.

## Shared Search and Ask before serving

The isolated application also exposes `/candidate/search` and `/candidate/ask`.
They invoke the same presentation, packing, provider, citation and fresh-source
checks as the public orchestrators, with an explicit closed `CandidateContext`.
Public entrypoints still reject `CandidateRetriever`; the context is never a
request field and the private app refuses a production environment. There is
no quota consumption, authenticated-user operation or saved-answer insertion.

Private responses use a separate engineering metadata version/scope and the
actual content/build/validation/legacy-predecessor records. Their common
`content_snapshot` mode describes the immutable data, while the distinct
engineering version and `owned_restore_not_activated` scope explicitly deny
serving authority. No activation ID is created. Public metadata serialization
and saved-evidence contracts continue to reject this candidate identity.

For the actual initial corpus, the operator must measure the complete derived
parent inventory. A zero-parent numerical path may report its real empty
inventory. Positive scientific parent bindings require the separate activated
public contract; the engineering path reports unavailable rather than hiding
positive data or inventing activation-bound result IDs. Public positive-parent
behavior remains covered by its actual synthetic SQL tests. This narrow private
scope must be retained in real-corpus reports and cannot be called public-route
or scientific acceptance. Generated answers still carry the existing support,
packing and currentness dispositions; a200 response alone is insufficient.
