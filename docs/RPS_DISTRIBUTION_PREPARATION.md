# Exact RPS source-binding and descriptor preparation

Contract: `rps-distribution-preparation/1.0.0`.
Issue: [ML07 / #68](https://github.com/JackZH26/SCLib_JZIS/issues/68).
Related: [distribution governance](RPS_DISTRIBUTION_GOVERNANCE.md) and
[dependency rights workbench](RPS_RIGHTS_PREPARATION.md).

## Purpose and authority

An authenticated curator can now register an existing, independently pinned RPS
release/public bundle without first inserting its internal descriptors directly
in SQL. The preparation API creates only the existing controlled descriptor
artifacts and a sealed private distribution package. It reuses the unchanged
source-binding, complete-inventory and registration validators.

This is an API workflow, not a new browser source-selection workbench. Its
committed package UUID can be opened in the existing rights workbench at
`/dashboard/research/distributions`. Actual source ingestion, scientific
adjudication, rights decisions, independent package review and third-account
publication remain separate operations. No score, license, review, research
role, new property family, ML-use permission or superconductivity label is
generated by preparation.

## Inputs and exact source selection

The closed POST body contains `request_key`, `release`, `selections`,
`public_bundle`, `expected_release_sha256`, `expected_selections_sha256`,
`expected_public_bundle_sha256`, `artifact_bytes_base64`, optional
`capsule_artifact_bytes_base64`, optional `expected_intent_sha256` and `dry_run`
(default true). Commit requires the preview's exact `expected_intent_sha256`.
Client actor IDs, extra fields, URLs to fetch and filesystem paths are forbidden.

Release and public-bundle pins use their existing versioned manifest/bundle hash
contracts, not an improvised whole-file checksum. The original release must
exactly equal the complete release inside the verified public bundle. The
selection pin hashes the complete canonical selection document using the
existing Python `research_priority.canonical_json`/`digest` contract. A different
language's default JSON float serializer is not an interchangeable hash format.

The selection document has exactly three fields:

```json
{
  "version": "rps-distribution-selections/1.0.0",
  "evidence_roots": [
    {
      "artifact_id": "<RPS-evidence-ID>",
      "root": {
        "kind": "frozen_result",
        "manifest_sha256": "<actual capsule manifest hash>",
        "table": "event_properties",
        "row_id": "<actual property UUID>",
        "row_sha256": "<independently expected complete property row hash>"
      }
    }
  ],
  "identities": [
    {
      "artifact_id": "<RPS-material-or-state-ID>",
      "table": "materials",
      "row_id": "<actual database material ID>",
      "row_sha256": "<independently expected complete row hash>"
    }
  ]
}
```

This illustration contains placeholders and is not a runnable request.
There must be one explicit root for every evidence
artifact and one exact identity for every material/state artifact. State
identities use `material_states` and the actual UUID. Formula similarity does
not select a material, phase, sample, pressure or state.

| Root kind | Exact fields, including `kind` | Existing admission |
| --- | --- | --- |
| `source_capture` | `source_revision_id`, `source_revision_record_sha256`, `capture_id`, `capture_record_sha256`, `bytes_sha256` | Actual pinned revision/capture, bytes and accepted Paper-to-Work mapping; literature evidence only |
| `frozen_result` | `manifest_sha256`, `table`, `row_id`, `row_sha256` | Actual 0054 capsule with exact claim/property and complete verified rows/bytes |

The `artifact_bytes_base64` map contains exactly the bytes required by the live
source/identity closure, keyed by their actual SHA-256. Each frozen capsule's
complete byte map is separately keyed by its manifest hash. Extra, missing or
substituted payloads reject. Shared identical bytes can deduplicate; distinct
logical references and full dependency closure are not discarded. Generated
descriptor bytes are not uploaded in either source map.

The server reads actual database rows under its transaction. Supplied row JSON
is not accepted as a database observation. Frozen evidence retains the complete
capsule's permission inventory, not only the displayed result. Existing origin
rules remain: a native pending import with an `extraction` event and `Computed`
property is not automatically a `calculation` event. Preparation cannot relabel
it to bypass the frozen result contract or scientific review.

## Descriptor bytes, stable preview and atomic commit

Every non-evidence artifact becomes one restricted EvidenceArtifact using the
existing `rps-artifact-record/1.0.0` schema and existing kind mapping. It has no
URI or assigned license. Its actual bytes are the canonical complete original
RPS artifact **including that artifact's own `sha256` field**. The resulting
byte/record hash is not the artifact's embedded hash, which covers the complete
artifact excluding its own `sha256` field.

Metadata retains the exact UTF-8 JSON text as `rps_artifact_json`, plus the
preparation version and captured-request hash. Storing that text inside JSONB
preserves forms such as `-0.0`; storing a nested JSONB artifact object would
normalize numeric representations and could destroy exact hash reconstruction.
The source/version marker identifies the preparation format, not a cryptographic
process attestation or human endorsement. `hash_status=verified` refers to
actual-byte integrity, not scientific truth.

Preview exercises real inserts, old validators and deferred SQL completeness
constraints, then rolls back descriptors, package, dependencies and guard epochs.
A new preview returns `package: null`; its temporary UUIDs and timestamps are
not durable references. The stable intent binds:

- Authenticated curator and exact grant, original request key and version/scope.
- Independently pinned release, public bundle and selection/actual-byte request.
- Every source dependency's exact sealed projection, including all capsule rows.
- The complete ordered generated descriptor byte plan and dependency counts.

The stable intent uses the generated descriptor byte plan instead of generated
database-row projections. Complete generated projections, including timestamps,
remain in `inventory_sha256`; exact generated IDs remain in `bindings_sha256`.
No source row is omitted to make a stale preview pass. Two valid previews can
therefore share an intent while their temporary inventory hashes differ.

Commit rebuilds and validates the real complete inventory and compares the exact
preview intent before the outer commit. A mismatch rolls back everything. The
internal service always reports `committed: false`; only the enclosing HTTP
operation can report durable completion after its transaction commits. Response
serialization and the 8 KiB response bound are checked before that commit.

## Routes, replay and acknowledgement loss

All routes use `/v1/ml/distributions/preparation` and the existing ML foundation
feature flag, verified account, explicit active curator grant and browser CSRF
policy. Capability checks are informational; the final transaction independently
checks the current account/session/grant. Legacy administrator flags do not
substitute for a research grant. Responses and errors are private/no-store.

| Method and suffix | Result |
| --- | --- |
| `GET /capabilities` | Current curator/account/grant capability, without publication authority |
| `POST` at the prefix | Rollback-only preview or explicitly pinned atomic registration |
| `GET /outcome?request_key=...&expected_intent_sha256=...` | Original account's exact historical registration, without writes |

An identical POST resolves a retained actor/key registration before creating
descriptors or fetching current sources. It returns the same durable IDs with
`replayed: true` and persists no records or guard-epoch changes. A changed request
or preview pin rejects. POST also requires the original exact grant. Its initial
static release/bundle verification still uses the installed verifier, so this is
not a promise of write replay across incompatible future implementations.

GET outcome verifies the sealed package and descriptor projections, not mutable
live descriptor rows. It neither reconstructs a new registration nor checks
current publication eligibility. A replacement active curator grant for the
same original account may recover historical intent containing the original
grant. Another account cannot recover that receipt by knowing the key.

GET returns 404 when the exact original key is not observed in that snapshot,
and 409 for a mismatched intent. Neither absence nor a transport failure proves
rollback. Preserve the original account, request key and preview hash in the
approved private operation record. Inspect the original outcome before deciding
on a separate explicit same-request retry; never silently generate a new key.

All returned `scientific_acceptance`, `ml_training_approved` and
`current_authorization_checked` flags remain false, including after a historical
receipt is recovered. Subsequent rights/review/publish and the unchanged live
public admission gate are still required.

## Resource bounds and verification scope

The new HTTP route bounds the raw query to 1,024 bytes before framework parsing,
the body to 48 MiB / 65,536 stream chunks, and all decoded source/capsule bytes
to one shared 32 MiB budget. Existing per-file 8 MiB, eight-capsule,
5,000-binding, 20,000-dependency and canonical depth/node constraints still
apply. The generated descriptor map and complete verifier retain their existing
64 MiB ceilings. These separate ceilings cannot all necessarily be combined.

The existing two-slot nonwaiting per-process admission gate, 10-second upload
timeout, 30-second request timeout and bounded SQL statements are reused.
Synchronous parsing/hashing is size-bounded; an asyncio deadline is not a claim
that CPU-bound work is preemptible. These are engineering caps, not measured
production throughput or fleet-wide memory guarantees.

Native tests use disposable synthetic sources and real PostgreSQL transactions,
including preparation through rights, independent review, publication, live
admission and revocation. Their outcome is software verification, not a real
rights decision, approved pilot, corpus-sized benchmark, deployment or ML study.
No schema migration is added by this increment.
