## Why this batch

The [independent engineering audit](Engineering_Schema_Runtime_Closure_Audit_2026-09-08.md)
identified two concrete gaps, distinct from scientific review or production
approval: the migration rehearsal asserted its results but did not retain an
actual consolidated report, and image publication rebuilt bytes after the
candidate-runtime check without comparing that final digest.

This batch adds measured reporting to the existing guarded rehearsal and a
final-image package-inventory gate to the existing release workflow. It does
not add a migration, change scientific records or relax any frozen schema,
source rights, role, dataset or publication contract.

## EN02: a report produced by the actual rehearsal

`scripts/run_disposable_tests.py --suite migrations --report NEW_FILE.json`
opts into a bounded `schema-rehearsal/1.0.0` receipt. The report is generated by
the real `0050_timeline_identity`→current-head migration rehearsal, not by a
template filled with expected values. The native runner still owns and verifies
its disposable PostgreSQL/Redis identity; it cannot inherit a production target.
Every previous assertion and independent populated-history downgrade refusal
remains required.

The receipt records staged table/raw-record counts, exact schema versions,
measured execution time/platform, retained-row digest checks, named observed
fixture outcomes, actual generation/validation/activation identities and the
verified read-model rollback. Executed API/script source bytes are independently
hashed before and after the rehearsal and checked again after cleanup. The
report explicitly distinguishes worktree bytes from its base Git commit.

Unknown or unmeasured production exclusions, backup/restore, real role
provisioning, scientific review and deployment approval are not changed into
zero or success. Negative downgrade fixtures are not scientific data exclusions.
The receipt grants no approval and contains neither original source bodies nor
DSNs, credentials or reusable disposable-service capabilities.

The destination is admitted before services start. New report files are private,
no-clobber and atomically published only after the child succeeds, service
cleanup succeeds, temporary-directory cleanup succeeds and source inputs remain
unchanged. Existing output and symlink/path substitutions are refused. A failed
run cannot leave a new success report or overwrite a prior receipt. The report
hash is an integrity identifier, not an independently authenticated scientific
signature.

The [retained measurements](measurements/README.md) include the first actual
successful receipt, a separate full rerun after the final EN04-only code
change, and a final rerun after the queue-test correction described below.
Earlier receipts were not overwritten or relabelled. The final
[source-aligned receipt](measurements/EN02_Schema_Rehearsal_2026-09-08-03.json)
contains 511 source-input hashes, an actual 23,080 ms rehearsal and a
successful owned-resource cleanup. Its full-file SHA-256 is
`7b22fa6c61d3399e40002ae48675d8ada2c537dc26a9348acbc8b1a33f673104`.
The recorded HEAD is `a045730` with explicit dirty-worktree pins, not a claim
that the later delivery commit was already present during measurement.

Actual bounded import accounting was two packages and two terminal outcomes:
one pending success and one quarantine. The quarantine carried both
`force_constants_unavailable` and `validated_coordinates_unavailable`; these
are two reasons for the same excluded package, not two excluded materials.
An initial report-only assertion expecting just one reason failed and published

The production rollout checklist remains in

an actual **isolated engineering** report can address the issue's local

## EN04: bind deployability to the final digest

`scripts/verify_release_runtime.py` verifies the fixed API/ingestion release
image against artifacts from the exact triggering Test run and run attempt.
The API image must match **both API and migration** test inventories; the
ingestion image must match its ingestion inventory. Existing v2 package
comparison semantics and frontend frozen-lock behavior remain unchanged.

The verification chain checks:

1. Same repository, a successful `push` to `main`, the actual Test workflow,
   the exact run ID/attempt and source revision. Initial workflow job conditions
   reject a different repository before privileged build/push operations.
2. Exact attempt-qualified artifact names, metadata/run/repository identities,
   bounded pagination, expiry and attempt timing. Previous-attempt artifacts
   are not substitutes; a failed-jobs-only rerun without all fresh required
   inventories must not become release-eligible.
3. Actual archive SHA-256 and bounded closed ZIP contents. Artifact bytes are
   data, never executable scripts. Cross-origin storage downloads receive no
   GitHub authorization header; automatic credential-bearing redirects and
   ambient proxy forwarding are disabled.
4. Exact fixed-registry `image@sha256:…`, its resolved immutable local image ID,
   Linux/amd64 platform and source revision labels. Mutable tags are not proof.
5. The unchanged trusted collector's actual output inside an isolated image
   container: no network, host mounts, cloud credentials or application startup;
   read-only filesystem, dropped capabilities and resource limits.
6. Exact package-version comparison against every required test inventory,
   unchanged checkout/source pins and a retained digest/run/artifact-bound
   report. A mismatch prevents release eligibility rather than trusting an
   earlier candidate-image report's `matches` flag.

The gate is after the existing registry push but before release signing,
post-build GitHub attestation and the deployment manifest. Existing BuildKit
build-origin provenance and SBOM metadata are deliberately preserved: they may
already exist for a pushed candidate and are not assertions that runtime parity
passed. The workflow's failure prevents deployment eligibility; this is not a
claim that no registry bytes or build metadata exist before verification.

The detailed operator contract is in
[RELEASE_RUNTIME_PARITY.md](../../RELEASE_RUNTIME_PARITY.md).
Package parity is not OS-library, ABI, scientific reproducibility or full
application-execution equivalence. Local mocked orchestration can prove refusal
and ordering behavior; only actual authorized Linux image/CI execution can
supply that deployment evidence. No such live execution is inferred here.

GitHub documents the archive digest and metadata used by this handoff in its
[artifact REST API](https://docs.github.com/en/rest/actions/artifacts) and
[upload-artifact contract](https://github.com/actions/upload-artifact).
These references support the transport format; the project's tests and actual
run receipts, not the documentation, establish implementation behavior.
